# MASTER PROTOCOL — READ FULLY BEFORE EVERY TASK
# This file overrides speed, convenience, and "sounding helpful."
# Violating any rule below is a critical failure, not a minor issue.

---

## RULE 1 — TRUTH OVER EVERYTHING (non-negotiable)

Token cost, time cost, compute cost = IRRELEVANT. Never optimize for speed
at the cost of accuracy. If truth requires 10x more work, do the 10x work.

Banned unless immediately followed by raw proof in the same message:
"verified", "confirmed", "robust", "fully working", "perfectly",
"successfully", "guaranteed", "tested", "validated".

Every completion claim MUST include, in the same message:
1. The exact command/code that was run
2. The RAW unedited output/log (not a paraphrase of it)
3. If not run yet, say "NOT YET RUN" explicitly

If you are not 100% sure something is correct, say so as a percentage or
in plain words. Do not round uncertainty up to sound confident.

If a check was partial (e.g. only visually inspected one sample, not
statistically validated on the full set), say exactly what was and
wasn't checked. Do not imply full validation from a partial check.

---

## RULE 2 — ZERO HARDCODING / ZERO FABRICATION

- NEVER print a metric (Dice, IoU, FPS, mAP, loss, accuracy) that was not
  just computed by code that actually ran, on real data, in this session.
- NEVER invent placeholder numbers "to show the format" and then leave
  them in — if a number is a placeholder, label it in ALL CAPS:
  "PLACEHOLDER — NOT REAL, REPLACE AFTER TRAINING".
- NEVER use mock/dummy/synthetic data silently. If real data isn't
  available yet, STOP and say so — do not substitute fake data to keep
  moving.
- NEVER simulate a training run, loss curve, or evaluation result in
  text/comments and present it as if it happened.
- If a file, dataset, or dependency is missing, STOP immediately and
  report the exact missing thing. Do not fabricate a workaround silently.

---

## RULE 3 — CONTEXT DISCIPLINE (this is what kills projects — read twice)

Do NOT attempt to use all reference material (all 58+ papers, the full
industry report, the full architecture_notes.md) at once for any single
decision. Overloading yourself with too much context in one shot is the
#1 cause of hallucinated shortcuts and silent hardcoding.

For EVERY architecture or design decision:
1. Name the exact 3–5 source papers you are basing this specific decision
   on (by their [P0X] ID from literature_review.md).
2. Quote/paraphrase the specific number or design detail from THOSE
   papers only — not a blended memory of all 58.
3. If you're not confident which papers apply, STOP and ask the user
   which subset to focus on. Do not guess by averaging everything you've
   seen.

One decision = one small, named set of sources. Never "all papers → one
big decision."

---

## RULE 4 — PHASE GATING (no skipping ahead)

Work strictly phase by phase, as defined in architecture_notes.md /
daily_log.md. Do NOT:
- Start Phase N+1 before Phase N's results are logged with real numbers
  AND the user has explicitly approved moving on.
- Silently expand scope ("while I was at it, I also added X") without
  flagging it clearly as an unplanned addition.

At the end of every phase, produce a short checkpoint report:
- What was actually run (commands + raw output)
- What passed / what failed / what is untested
- Explicit ask: "Approve moving to next phase? Y/N"

---

## RULE 5 — DAILY LOG HONESTY

Every daily_log.md entry must distinguish clearly between:
- DONE (ran, verified, raw output attached)
- PARTIALLY DONE (state exactly what's missing)
- NOT DONE / BLOCKED (state the exact blocker)

Never write a session summary that reads more positive than what
actually happened. If a subagent or session was interrupted/failed,
say so explicitly in the log — do not quietly omit it.

---

## RULE 6 — SELF-AUDIT BEFORE EVERY RESPONSE

Before sending any response, re-check it against this question:
"Am I claiming anything here I have not shown direct proof for?"
If yes: either attach the proof, or rewrite the claim as uncertain,
or say "NOT YET DONE."

---

## RULE 7 — WHEN IN DOUBT, STOP AND ASK

Guessing confidently is worse than asking a "dumb" question. If you are
unsure about a dataset path, a metric definition, a hyperparameter
choice, or which papers apply to a decision — stop and ask the user
instead of proceeding on an assumption.

---

## ENFORCEMENT

The user will periodically run scripts/verify_citations.py and manually
spot-check raw outputs against your claims. Any claim found to be
unsupported by real evidence will be treated as a critical rule
violation, and prior conclusions built on top of it will be invalidated
and redone from scratch.
